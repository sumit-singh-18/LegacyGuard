# Validation run 2: the nine BugsInPy bugs after Sprint 5 (2026-11-14, DRAFT)

Second run on the same nine bugs as run 1 (`2026-11-bugsinpy.md`), on main at 2de7f4a (Sprint 5 merged).
Harness: `tools/validate.py tools/validation/manifest.yaml --fix-tests both`. Raw results:
`2026-11-run2-results.json`. Interpreter: Python 3.10.22 for every case. Produced by the implementer agent;
every detection below was checked by calling the fixed and buggy code directly (package archives of each
commit). Not yet reviewer-checked.

Method as in run 1, with one change: each bug now runs twice. **Without fix tests** (the headline) uses a
synthetic base commit in which the test files the fix changed are put back to the buggy commit's version,
so the regression test the fix added does not exist. **With fix tests** uses the fixed commit as is. Run 1
reported "without" from a one-off script (test files reverted in the working tree); the numbers are
comparable, the mechanism is not identical.

Notes on the detections:
- youtube-dl 10's deciding input starts with `"{abc_def:'1\'\\2\\\'3"`, a valid JavaScript double-quoted
  string containing a `\'` escape (only its trailing `4'}` is junk). The fixed code keeps that string token
  whole; the buggy regex accepts only `\\` and `\"` escapes inside double quotes, so it splits the token. That
  is the bug's root cause. A well-formed example, checked directly: `js_to_json('{"k": "a\\\'b"}')` returns
  `'{"k": "a\\\'b"}'` fixed and `'{"k": ""a"\\\'"b""}'` buggy. Several other differing inputs (10 in
  "without" mode) are edit-derived regex samples containing `\n` and `\u` escapes; only the clean shape
  `'"a\\nb"'` was missing.
- With fix tests, the fix's own youtube-dl 10 input (now resolved through its variable `inp`) **timed out**
  in the buggy version: the buggy regex backtracks catastrophically on it (23 s by direct call; the worker's
  limit had dropped to 0.5 s after earlier timeouts). A timeout in the new code against a fast return in the
  old is not counted as a difference today.

## Misses, diagnosed

1. **youtube-dl 1 without fix tests: propagation; edit inputs never saw a dict.** `_match_one` is
   "verified" on 40 inputs, all of them carved from `match_str`'s pre-fix test calls (`{'x': 1200}`,
   `{'x': 0}`, `{}`); planted bugs 4 of 8. The edit's dict-value splicing (Task B) builds its variants from
   the function's own example calls; `_match_one` has none (tests call `match_str`), so it fell back to
   placeholder bases and produced two inputs (`'!'`, `''`), both rejected as invalid filters. Carved calls are
   merged after the edit inputs are built, so they are never used as bases; callers (`match_str`) get no edit
   inputs at all (`not t.via`). `_match_one('x', {'x': False})` (False vs True) and
   `match_str('x', {'x': False})` both distinguish the versions (checked). Mechanism that should have reached
   it: B (edit dict values) applied to E's carved calls.
2. **youtube-dl 5 without fix tests: coverage.** "reached 2 of 3 changed statements; line 1118 never ran":
   the buggy `return calendar.timegm(timetuple.timetuple())` runs only when no strptime format matches and
   `email.utils.parsedate_tz` succeeds. None of the pre-fix examples does that (checked: `'2/2/2015 6:47:40 PM'`,
   `'Feb 14th 2016 5:45PM'`, `'2012/10/11 01:56:38 +0000'` all parse earlier), and splicing the edit's tokens
   (`PM`, `(?i)PM`) into the pre-fix examples gives no difference in any of 120 splices (checked). Inputs that
   would: `'Dec 14, 2012 11:15 PM'`, `'Mon, 16 May 2016 23:15:00 +0000'`. No Sprint 5 mechanism targets a
   branch condition (`if timetuple:`) the input must satisfy.
3. **tqdm 4, both modes: coverage.** `format_meter`'s changed statement sits under
   `if unit_scale and unit_scale not in (True, 1)`; the bug needs a numeric `unit_scale` and `total=None`
   (`format_meter(10, None, 1, unit_scale=10)`: `'100it [...]'` vs TypeError, checked). Of 500 inputs,
   `unit_scale` was only True or False and `total=None` appeared once. Carving (E) recorded 4 calls, all from
   callers run on default-built instances (`unit_scale=False, total=10`). Edit inputs (B) produced none: the
   changed statement (`if total:`) holds no literal; the constants `(True, 1)` are in the guarding condition.
   The fix test drives it through `tqdm((i for i in range(10)), file=our_file, unit_scale=10)`, a constructor
   with a generator argument, which the guard does not build or run. Roadmap E's acceptance asked for "a
   stated reason why not": this is it.
4. **thefuck 7, both modes: selection.** Objects are now built from tests (B works: every example is a
   `Command(...)`), but the 37 example inputs come from other rules' tests (`ssh`, `systemctl`, `git`,
   `manage.py`, `sed`); none is a `php` command. `match` is a common name; example files are chosen by call
   count, at most 8 (`MAX_FILES`), and the rule's own `tests/rules/test_php_s.py` (it imports `match` from
   `thefuck.rules.php_s`) is not among them. With it, the fix test's `Command('php -t pub -s 0.0.0.0:8080', '')`
   gives True vs False (checked). Without fix tests, even the right file holds only `Command('php -s ...')`,
   which both versions accept; the edit's fragments would have to be spliced inside the `Command` arguments,
   which edit splicing does not do.
5. **thefuck 1, both modes: selection and coverage.** Same selection problem (examples are `sed`, `git`,
   `apt`, `brew` commands; all raise IndexError in both versions, so "no input ran to completion"). The rule's
   own test builds its output through fixtures and `str.format`
   (`'ERROR: unknown command "{}" - maybe you meant "{}"'.format(broken, suggested)`, with `broken` and
   `suggested` overridden by parametrize), which would also have to resolve. Checked directly:
   `Command('pip un+install thefuck', 'ERROR: unknown command "un+install" - maybe you meant "uninstall"')`
   gives `'pip uninstall thefuck'` vs IndexError.

## What this shows

1. **Task A did what it promised.** Seven "verified" results and one "quiet" case were unsupported and are
   now reported as untested/unchecked. That is most of the rise in untested share (65% to 77-79%); 28 of the
   40-41 untested functions are youtube-dl extractor callers: 26 with no input that ran to completion,
   2 whose inputs ran but never reached the changed lines.
2. **Edit-derived inputs (B) are the main new source of detections**: three cases without fix tests
   (youtube-dl 3, 10, tqdm 9). They worked where the edit's literal lands in a string or number argument of
   the edited function's own example calls.
3. **The remaining misses are about where inputs come from, not about the comparison.** No miss is
   environmental. Two are selection (thefuck: the right test file is not picked), one is propagation
   (yt-1: carved calls not used as bases for edit inputs), two are coverage behind a branch condition
   (tqdm-4, yt-5).
4. **A new kind of symptom was left on the table**: the buggy js_to_json hangs on the fix test's input
   (23 s). A new-only timeout is evidence of a regression too.

## Next steps (ranked by misses each would turn into detections; reviewed)

1. **Use carved calls (and callers' example calls) as bases for edit inputs.** Expected: youtube-dl 1
   without fix tests (`{'x': False}` from the carved `{'x': 1200}`, checked).
2. **Prefer example files that import the function from its own module** before ranking by call count, so a
   common name (`match`, `get_new_command`) gets the rule's own tests. Expected: thefuck 7 with fix tests
   (checked); thefuck 1 also needs fixture `str.format` resolution.
3. **Splice edit literals into the string arguments of constructed objects** (`Command(script, output)`).
   Needed for thefuck 7 without fix tests; unverified that a splice of `" -s "` produces a distinguishing
   script.
4. **Inputs aimed at the condition that guards a changed statement**: constants compared in that condition
   (`not in (True, 1)` suggests 2, 10) crossed with None for the other parameters, and a library-format pool for
   date-like strings. Targets tqdm 4 and youtube-dl 5; the least certain of these.
5. **Skip callers that cannot be called** (26 extractor callers per youtube-dl run ran no input to completion;
   they still use time and the 12-function budget). Saves time; turns no miss into a detection.

New kinds of evidence (not ranked by misses; none of these turns a miss above into a detection):
- **A slowdown result for a timeout only in the new code.** The fix test's own youtube-dl 10 input makes the
  buggy regex backtrack for 23 s, while the old code returns at once; youtube-dl 10 is already detected, so this
  adds evidence, not a detection. It is easy to make noisy (the per-call limit drops to 0.5 s after two
  timeouts, and three workers share the sandbox), so it would need: both old runs returning within a small
  share of the full limit (say 10%); the new code re-run alone on that input with the full limit and timing out
  again; the old code re-run alone and still fast; no check when the reduced limit is in force; and its own
  "slowdown" result, never "different", never counted as a detection by the harness, worded as a slowdown and
  not a proof. In "with" mode these timeouts probably also used time later inputs needed (4 differing inputs
  vs 10 without; the p95 case at 12.5 s); inferred, not traced.
